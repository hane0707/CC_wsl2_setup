結論（先に3行）

Finding 1 — PR は「作れない」のではなかった

実際に環境を叩いて検証した結果、GitHub への PR 作成に必要な通信・認証・書き込み権限はすべて正常に通っています。原因はサンドボックスではなく、gh pr create というコマンドが人間との対話を前提にしていることでした。設定を変える話ではなく、コマンドの呼び方を決めておく話です。

Finding 2 — 画面確認は、壁を緩めずに実現できる

サンドボックス（安全の壁）が制限しているのは Bash コマンドだけです。ブラウザ操作を担当する MCP サーバーは壁の外で動くため、セキュリティ設定を一切ゆるめずに「AI が画面を見る」を追加できます。

Finding 3 — むしろネットワークの壁に穴が空いていた

許可リストに入っていない https://example.com に、確認もなく接続できてしまいました。現在の allowedDomains は「通してよい先の一覧」ではなく「いちいち確認しないで済ませる一覧」として動いています。今回の改善で、ここを本当の遮断に切り替えます。

つまり今回の作業は「セキュリティを削って便利さを買う」のではなく、不満を解消しながら同時に安全性も上げられるという珍しい状況です。以下、根拠と手順を順に説明します。

1

前提：Claude Code の安全のしくみを3分で

この後の議論を正しく理解するために、Claude Code が持っている「安全装置」が 2種類あって性質が違うことだけ押さえてください。ここを混同すると、今回の結論がまるごと誤解されます。

図1 — 2種類の安全装置と、その適用範囲

覚えておくべき一点：サンドボックス（②）は Bash コマンドにしか効きません。MCP サーバーは①の許可ルールでは管理されますが、②の壁の中には入りません。これが「画面確認を安全に足せる」根拠であり、同時に「MCP を増やすと壁の外の経路が増える」というリスクの根拠でもあります。

なぜ WSL2 + サンドボックスが優秀だったのか

①だけの環境（Windows でそのまま動かす場合など）は、AI が「見た目は無害だが実際は危険なコマンド」を書くと通ってしまう可能性が残ります。②があると、たとえ AI が誤ったコマンドを実行しても OS が物理的に拒否します。この二重構造が現行環境の最大の資産で、今回の提案でも壊しません。

3

不満① 「PR が作れない」の真因

第2章の実測から、原因はネットワークでも権限でもないと確定しました。残る最有力候補は gh pr create というコマンド自身の性質です。

図2 — なぜ止まるのか：人間向けの作りと、AI の実行環境のズレ

「ブランチ作成と git push は問題なくできていた」という体験とも整合します。それらは質問してこないコマンドだからです。gh pr create だけが対話を要求します。

解決策：手順を skill として固定する

毎回 AI に正しいフラグを思い出させるのではなく、「PR を作るときはこの手順」を文書化して読ませるのが確実です。Claude Code ではこれを skill（作業手順書ファイル）と呼びます。commit-commands プラグインの /commit-push-pr が既に近いものを持っているので、そこに非対話フラグを固定した自前 skill を用意します。

フォールバック（万一 gh が使えない場合）

gh api -X POST /repos/<owner>/<repo>/pulls \
  -f head=<branch> -f base=main \
  -f title="タイトル" -f body="本文"

なぜこれで確実か：gh api は REST API を直接叩くだけのコマンドで、対話 UI を一切持ちません。第2章でこの経路が通ることは実測済みです。

図3 — 画面確認の3ルート
ルートできること利点欠点

推奨		 画面のスクショ取得、クリック・入力の自動操作、コンソールエラーの取得、要素構造の把握 設定が簡単。同じ仕組みを自動テスト（CI）でも使い回せる。無人実行に強い 実ブラウザの「人間が見ている画面そのもの」ではない。WSL2 では並列実行時にクラッシュしやすく、GPU 無効化フラグが必要

推奨：案1 を土台に、案3 を段階的に重ねる

図6 — 3段階ロードマップ

なぜこの順番か

  • 不満①はアーキテクチャの問題ではなかったため、環境を作り直す必要がありません。作り直しは最もコストが高く、最も失敗しやすい選択です
  • 不満②は壁を緩めずに解決できるため、セキュリティを差し出す取引が発生しません
  • 目標である時間ベースの自律化には GitHub Actions が事実上必須で、これは STEP 1 の上にそのまま積めます（排他ではない）

STEP 1 の完了判定：実際に PR を作って確かめる

第3章の結論は「経路は正常、原因は対話性」という推定です。机上で終わらせず、この設定変更そのものを題材にして実際に PR を1本通します。設定変更の成果物（settings.json の差分・新規 skill・本提案書）は、ちょうど PR にするのに手頃な粒度です。

手順やること確認したいこと
1作業ブランチを切る従来どおり成功するはず（既に実績あり）
2設定変更・skill・提案書をコミット同上
3git push -u origin <branch>同上。ここまでは元々問題がなかった箇所
4gh pr create を非対話フラグ付きで実行ここが本番。成功すれば「対話性が真因」が確定し、skill の型も同時に検証できる
5失敗した場合：エラー全文を記録し gh api -X POST で再試行それでも失敗するなら真因は別にある。エラー内容から切り分け、本書を改訂する
この検証が STEP 2 の前提になる理由

自律実行では「PR 作成」が人間の目に触れる最初の成果物になります。ここが不安定なままループを回すと、AI が最後の一歩で毎回詰まり、原因究明に時間を取られます。手で1回通してから自動化する——この順序を守ってください。

自律化の4段階（今回の目標地点）

段階誰が終わりを決めるか備考
1. ターンベース人間が毎回確認現状。指示するたびに結果を見る
2. ゴールベース /goal検証可能な条件STEP 1 の到達点。「テストが全部通るまで」等を条件にすると、AI が自分で直し続ける
3. 時間ベース /schedule・ActionsスケジュールやイベントSTEP 2 の到達点。ただし「Issue に書けば AI が着手する」形の運用を採るかは未確定。当面は人間が手動で指示を出す前提とし、Actions と Issue 発火は任意の選択肢として保留する
4. プロアクティブAI 自身が仕事を探す今回は対象外。コストと暴走管理が別途必要
自律化で最も重要な原則

Anthropic のハーネス設計に関する公式記事は、「AI に自分の成果物を評価させてはいけない」と明言しています。自己評価は実際の品質より高く出るためです。したがって STEP 2 では、作る役と検証する役を分離し、検証は「テストが通ったか」「画面にエラーが出ていないか」といった機械的に判定できる条件に落とし込みます。不満②の解消（画面確認）は、実はこの検証役を成立させるための必須部品でもあります。

なぜ *.github.com を足すか：PR 作成は api.github.com という別のホストを使います。現状これが明示されていません（実測では通っていますが、それは第5章の「穴」のおかげであり、穴を塞ぐと同時に止まります）。

重要：github.com は消さずに残すこと。ワイルドカードの *.github.com がドメイン本体にマッチする保証がないためです。消すと git push が壊れる可能性があります。本体とワイルドカードは併記してください（registry.npmjs.org と *.npmjs.org も同様）。

なぜ strictAllowlist が必須か：これを入れないと、上のリストは「確認を省く一覧」にすぎません。入れて初めて「これ以外は遮断」になります。

なぜ他のドメインも足すか：遮断を有効にした瞬間、書き忘れたドメインへの通信が止まります。npm／pip／Node 本体の取得先など、実際に使われているものを事前に入れています。この一覧は各自の業務内容に合わせて追記が必要です（例：社内 npm レジストリ、Cloudflare、AWS など）。

8-2. 認証情報の保護：トークンを AI から隠す［今回は見送り／チーム配布時に採用］

決定：STEP 1 では採用しない

後述のとおり運用変更を伴うため、個人利用の段階では見送ります。以下はチーム配布（STEP 3）に進む際の推奨設定として記録しておくものです。設定内容と前提条件を先に把握しておくことに意味があるため、削除せず残します。

"filesystem": {
"denyRead": ["~/.ssh", "~/.aws", "~/.gnupg", ...]
},
+ "credentials": {
+ "files": [
+ { "path": "~/.ssh", "mode": "deny" },
+ { "path": "~/.aws/credentials", "mode": "deny" }
+ ],
+ "envVars": [
+ { "name": "GH_TOKEN", "mode": "mask",
+ "injectHosts": ["api.github.com"] }
+ ]
+ },

mask とは：AI が実行するコマンドにはニセの値を渡し、通信が api.github.com に出ていく瞬間だけ本物のトークンに差し替える仕組みです。AI はトークンの実体を一度も見ず、ログにも残りません。それでも認証は成功します。

重要な前提条件：この機能を使うには、①トークンが環境変数 GH_TOKEN に入っていることと、②network.tlsTerminate を有効にすることの両方が必要です。現在の環境ではトークンは ~/.config/gh/hosts.yml というファイルに保存されており、環境変数は未設定です（実測確認済み）。つまりこの設定は運用の変更を伴います。

見送った場合に残るリスク：トークンはファイル保存のままでも問題なく動作します。その状態で残る差分は「AI がトークンファイルを読める状態にある」という一点です。個人が自分の権限で自分のリポジトリを触る限り、これは許容範囲と判断しました。

チーム配布時には採用を推奨（申し送り事項）

複数人の環境で運用する場合、判断の前提が変わります。①権限の大きい共用トークンを扱う可能性がある、②誰か1人の環境で流出すると影響が全員に及ぶ、③個々人がトークンの取り扱いを正しく運用しているか管理者が確認できない——この3点により、リスクの重さが個人利用時と同じではなくなります。

そのため STEP 3（チーム展開）に進む判断をした時点で、この mask 設定を managed-settings 側に入れることを推奨します。mask は個人が上書きできる設定から指定しても無視される仕様（管理者と本人の設定でのみ有効）なので、組織強制と相性が良い機能です。前提として GH_TOKEN を環境変数に置く運用へ統一しておく必要があります。

"network": {
+ "tlsTerminate": {},
"allowedDomains": [ ... ]

これは mask を使う場合のみ必要です。通信の中身を書き換えるため、いったん暗号化を解く必要があるためです。mask を採用しないなら追加不要です。実験的機能である点にも留意してください。

8-4. 変更しないもの（重要）

項目据え置く理由
permissions.deny の一覧秘密ファイルや破壊的コマンドの拒否リストは現状のままで適切。サンドボックスと二重に効かせる価値がある
allowUnsandboxedCommands: false「サンドボックス外での再実行」を禁じる設定。ここを緩めると壁の意味が薄れる。維持を強く推奨
dangerouslySkipPermissions: "disable"全確認スキップの封印。無人実行は STEP 2 で CI 側に持っていくので、手元では封印したままでよい
filesystem.disabled案3 の要素だが STEP 1 では入れない。ファイル隔離を切ると、AI が自分の設定を書き換えて権限を広げる経路が生まれる
model: "opus"Opus 5 + Sonnet 5 の運用方針どおり。重い設計は Opus、定型作業はサブエージェントで Sonnet に振る使い分けが費用対効果に優れる
導入手順の注意

設定変更は一度に全部やらないでください。①まず *.github.com の追加だけ入れて PR 作成を試す → ②動いたら strictAllowlist を入れて数日運用しドメインを追記する → ③安定してから mask を検討、の順が安全です。strictAllowlist と mask を同時に入れると、失敗したときにどちらが原因か切り分けられなくなります。

9

追加する道具（設定ファイル以外）

9-1. Playwright MCP（画面確認）

claude mcp add playwright npx @playwright/mcp@latest -- --headless \
  --browser=chromium --viewport-size=1280,720 \
  --allowed-origins "http://localhost:*"

--headless：画面を表示せずに動かす。無人実行に必須。
--allowed-origins：AI が自動運転中に想定外のサイトへ飛ぶのを防ぐ安全装置。自律化を進めるなら必ず指定してください。
WSL2 特有の注意：ブラウザを複数同時に立ち上げると、WSL2 の GPU メモリ制約で連鎖クラッシュする既知の問題があります。並列実行を避けるか、GPU 無効化フラグを付けてください。

9-2. PR 作成 skill

「ブランチを切る → コミット → push → 非対話フラグ付きで PR 作成 → 失敗時は gh api で再試行」を1つの手順書ファイルにまとめます。AI が毎回同じ手順を踏むようになり、第3章の詰まりが再発しません。

配置先は ~/.claude/skills/create-pr/SKILL.md。チーム配布を見据え、本リポジトリの skills/ 配下でも同じものを管理し、そこから配置する運用にします。

実装時に判明した挙動：skill は Bash でコピーできない

サンドボックスは ~/.claude/skills/ への書き込みを OS レベルで拒否します（Read-only file system エラー）。AI が自分の手順書を勝手に書き換えるのを防ぐための保護です。

そのため cp や mkdir では設置できません。ファイル書き込みツール経由（サンドボックスの対象外）か、ユーザー自身の手でコピーする必要があります。第1章の「サンドボックスは Bash にしか効かない」の実例です。

9-3. 検証 skill（STEP 2 の中核）

公式のループ設計ガイドが推奨する形です。「完了」を AI の主観ではなく機械判定にします。

  • 開発サーバーを起動する
  • Playwright で対象ページを開き、実際に操作する
  • ブラウザのコンソールにエラーが出ていないか確認する
  • スクリーンショットを操作前後で比較する
  • 1つでも失敗したら、途中結果を返さず最初からやり直す

9-4. GitHub Actions［運用未確定・任意／STEP 2 の選択肢］

現時点では採用を保留

「Issue に書けば AI が着手する」形の運用を採るかは未確定です。当面は人間が手動で修正指示を出す運用を前提とするため、STEP 2 では検証 skill と /goal の型化を先に行い、Actions の導入はその必要性を感じた時点で判断します。
以下は、採用を決めた場合の要点として記録しておくものです。

/install-github-app を実行すると、GitHub App と必要な秘密情報の設定が対話で完了します。導入後は Issue や PR に @claude と書くだけで着手します。手動運用と併存できるため、後から足す形で問題ありません。

必ず設定する安全弁

実行のターン数と実行時間の上限を必ず設定してください。無限ループはコストに直結します。また、既定では書き込み権限を持つメンバーしか起動できませんが、権限は作業に必要な最小限に絞ってください。参考事例では週10〜15 PR の処理で月 $15〜25 程度とされています。

10

リスクと限界（誤解を避けるために）

サンドボックスは「完全な隔離」ではない

公式ドキュメントが明記している限界です。通信の中身までは検査していないため、*.github.com のような広い許可は情報の持ち出し経路になり得ます（例：秘密情報を書いた Gist を作られる等）。本当に強い保証が要る場合は、通信を検査する専用プロキシか、案2 のコンテナ隔離が必要です。

MCP を足すと壁の外の経路が増える

第1章のとおり MCP はサンドボックスの外で動きます。「隔離を緩めずに画面確認を足せる」のは事実ですが、MCP サーバー自体は信頼できるものだけを入れる必要があります。公式・準公式のものに限る、という原則を推奨します。

自律化はコストが跳ねる

ループは「止まらないと止まらない」仕組みです。停止条件を明確にすることが最大のコスト対策であり、同時に最大の安全対策です。/usage で skill・サブエージェント・MCP 単位の消費を定期的に確認してください。

この提案が前提としている未検証事項

第3章の「対話性が真因」は、状況証拠から導いた最有力の推定です（ネットワーク・認証・権限がすべて正常であることは実測済み、記憶が曖昧なため当時の症状は未確定）。第7章「STEP 1 の完了判定」で、この設定変更そのものを PR にして実地検証します。失敗した場合はエラー内容から切り分け、本書を改訂します。

11

用語集

サンドボックス（sandbox）
OS の機能を使って、コマンドが触れるファイルと通信先を強制的に制限するしくみ。AI がどんなコマンドを書いても OS が拒否するため、すり抜けられない。
permissions（許可ルール）
コマンドを実行してよいかを、実行前に文字列で判定するしくみ。サンドボックスと違い、書き方を変えられると通ってしまう余地がある。両方を併用する。
MCP（Model Context Protocol）
AI に外部の道具を持たせる共通規格。ブラウザ操作やドキュメント取得などを担当する小さなプログラムを常駐させる。サンドボックスの外で動く点が重要。
skill
AI に読ませる作業手順書のファイル。「PR を作るときはこの順番でこのフラグを使う」といった型を固定でき、毎回の指示が不要になる。
ハーネス（harness）
AI を長時間まともに走らせるための足場全体。手順書・検証・停止条件・役割分担などの総称。「AI に良い指示を出す」ではなく「AI が失敗しにくい仕組みを組む」という発想。
ループエンジニアリング
AI に同じ作業サイクルを繰り返させ、停止条件を満たすまで自走させる設計手法。/goal（条件で止まる）と /schedule（時間で始まる）が代表。
headless（ヘッドレス）
画面を表示せずにブラウザを動かすこと。人間には見えないが、スクリーンショットは撮れる。自動実行に向く。
managed-settings
組織の管理者が配布する、個人が上書きできない設定。チーム展開時に「全員がサンドボックスを有効にする」等を強制するために使う。
