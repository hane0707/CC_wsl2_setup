検証で判明した事実（実測データ）

セットアップの前提を左右する事実を、実際に手を動かして確認した。数値・エラー文言は実測そのものであり、推測は含まない。

検証項目実測結果
PR が作れない問題の真因 ネットワーク・認証・権限はすべて正常。証拠は POST /repos/.../pulls が 422 で応答したこと。422 は GitHub 側が内容を読んで返す検証エラーであり、経路上の障害がないことを示す。真因は gh pr create の対話 UI が人間の入力を前提にしている点だった。
allowedDomains は単体では遮断しない strictAllowlist が無いと「確認をスキップする一覧」として動く。実測で許可リストに無い example.com に 200 で到達できた。strictAllowlist 設定後は同じ未許可先が CONNECT tunnel failed, response 403 で遮断された。
サンドボックスは Bash コマンド1回ごとに使い捨てられる 観測されたプロセス番号は 1, 2, 389 という極めて小さい値。ネットワークインターフェースも lo（自分自身）のみ。コマンドごとにプロセス空間もネットワークも作り直されている。このため別コマンドや MCP のブラウザから、先に起動した開発サーバーに到達できない。
設定ファイルへの書き込みが黙って失敗する ~/.claude/.config.json、~/.mcp.json、.git/config（.git/config.lock 経由）に /dev/null がマウントされている。.git/config はエラーを返すが、.config.json は成功表示だけ出て何も残らない。claude mcp add が典型例で、「Added…」と表示されても再起動後に未登録だった。
書き込み先パスが実行場所で変わる 同じ MCP 登録コマンドでも、サンドボックス内実行では ~/.claude/.config.json、サンドボックス外（自分のターミナル）実行では ~/.claude.json に書き込まれる。後者のみ実体を持つ。
許可リストはリダイレクト先まで見ないと判断を誤る cdn.playwright.dev を許可リストに追加しても 307 で storage.googleapis.com に転送されるため通らない。後者は GCS（Google Cloud Storage）全体を指す広いドメインで、安易に許可すべきではない。
WSL2 の Ubuntu には日本語フォントが無い 実測で CJK フォント 0件。絵文字フォントも無い。この状態でヘッドレスブラウザのスクリーンショットを撮ると、日本語がすべて豆腐（□）になりアイコンも読めず、画面確認の用を成さない。
設定の反映タイミングが異なる settings.json の変更は再起動なしで反映される（実測確認）。一方 MCP の登録は起動時にのみ接続されるため再起動が必要。
422 応答の読み方

「422 エラー＝失敗」ではない。ネットワークが遮断されていれば、そもそもサーバーまで届かず接続エラーになる。届いて、認証され、内容を審査された上で「その内容では作れません」と言われた——つまり経路上の障害はゼロだと分かる。この切り分けが、原因をサンドボックスではなくコマンドの対話性だと特定する決め手になった。

2

設計判断（なぜこの構成なのか）

なぜこの設定を選んだのか、何とのトレードオフだったのかを記録する。

built-in サンドボックスを維持し、devcontainer に移行しなかった理由

PR が作れない問題も画面確認の問題も、環境全体を作り直さなくても設定とスキルの追加で解決できることが分かった。既存資産（設定・スキル・運用習慣）をほぼそのまま流用できる一方、アーキテクチャの変更は最もコストが高く、最も失敗しやすい選択になる。不満点が構成の欠陥ではなかった以上、構成そのものを変える理由がない。

MCP がサンドボックス外で動く性質を利用した理由

サンドボックス（隔離の壁）が制限しているのは Bash コマンドだけで、MCP サーバーは壁の外で動く。この性質を使えば、隔離を一切緩めずに「AI が画面を見る」機能を追加できる。
トレードオフ: MCP は壁の外の経路そのものなので、信頼できるもの（公式・準公式）だけを入れるという原則とセットで運用する。MCP を増やす＝壁の外の経路を増やす、という認識を欠かさない。

excludedCommands に開発サーバーを入れた理由

ブラウザ（MCP、壁の外）と開発サーバー（Bash 起動、壁の中）は互いに通信できない。画面確認を成立させるには、サーバー側も壁の外に出す必要がある。excludedCommands に登録したコマンドはサンドボックスの外で実行されるため、ブラウザと同じネットワークに立つ。
隔離は保たれる: 外に出るのはそのプロセスだけで、サンドボックス内からは依然としてそのサーバーに接続できない（実測確認済み）。壁自体が壊れるわけではない。
広いパターンを避ける理由: ここに登録したコマンドはファイルもネットワークも制限を受けなくなる。npm run dev のような具体的なコマンドに限定し、npm * のような広いパターンは登録しない。対象は自分のプロジェクトの開発サーバーに限定してリスクを最小化する。

プラグインを4つに絞った理由

プラグインは skill（作業手順書）を大量に持ち込む。skill が増えるほど AI が読む情報が増え、判断がぶれやすくなり、費用も増える。使う予定のないものまで残す必要はないため、実際に役割が噛み合うものだけを残した。削除は不可逆ではなく、必要になれば個別に戻せる。

GH_TOKEN の mask 化を見送った理由

今回は見送り／チーム配布時には採用を推奨

見送った理由: mask 化にはトークンを環境変数 GH_TOKEN に置く運用変更を伴う。現状トークンはファイル保存のままで問題なく機能しており、見送った場合に残る差分は「AI がトークンファイルを読める状態にある」という一点のみ。個人が自分の権限で自分のリポジトリを触る範囲では、これは許容できるリスクと判断した。

ただしチーム配布時には採用を推奨する。理由は3点。①権限の大きい共用トークンを扱う可能性がある、②誰か1人の環境で流出すると影響が全員に及ぶ、③各人がトークンを正しく運用しているかを管理者が確認できない。個人利用時とはリスクの重さが変わるため、チーム展開を判断した時点で改めて採用を検討する。

3

却下・保留した選択肢

検討したが今回は採用しなかったもの。将来同じ検討を繰り返さないための記録であり、「二度と採らない」という意味ではない。

devcontainer 全面移行

環境をコンテナ化すれば隔離は最も強くなるが、既存資産の作り直しが大きく、現状の不満は設定変更で解決できるため見送った。

採る条件: チーム展開フェーズで、環境差異の吸収そのものが目的になったとき再検討する。

ローカルの隔離を緩めて CI に厳格性を寄せる案

手元の作業を自由にする代わりに、危険な操作は GitHub Actions 側で最小権限実行する構成。時間ベースの自律化には適合するが、現時点では手元の隔離を弱める理由がない。

採る条件: 時間ベースの自律実行（Actions 常用）に本格移行する段階で、手元と CI の役割分担として組み込む。

storage.googleapis.com の許可

Playwright のブラウザ本体取得に必要だが、GCS 全体（任意のバケット）を指す広いドメインであり、サンドボックスのネットワーク隔離が持ち出し経路として大きく弱まる。ブラウザ導入はサンドボックス外（自分のターミナル）で一度きり実行する運用とし、恒久的な穴は開けなかった。

採る条件: 現時点では想定していない。同種の取得作業が頻発し、都度サンドボックス外で行う運用コストが無視できなくなった場合にのみ再検討する。

GitHub Actions による Issue 起点の自律実行

「Issue に書けば AI が着手する」運用。技術的な導入自体は容易だが、どこまで無人で着手させるかという運用方針が未確定のため保留した。

採る条件: 検証 skill と /goal の停止条件の型化が済み、時間ベースの自律化（第4章）に進む判断をしたとき。

Chrome DevTools MCP

Windows 側の Chrome と連携し、人間と同じ画面を AI が見られる。ただし Windows 側の設定変更（.wslconfig 編集や WSL 再起動）を伴い、無人実行にも不向きなため、任意の選択肢として保留した。

採る条件: デザインの最終確認や込み入った不具合調査で、人間が見ている画面をそのまま AI と共有したい具体的な必要が生じたとき。

4

自律化のロードマップ

段階的にエージェントの自律度を上げる計画。

段階誰が終わりを決めるか備考
1. ターンベース人間が毎回確認指示するたびに結果を見る、最も基本的な運用
2. ゴールベース /goal検証可能な条件「テストが全部通るまで」等を条件にすると、AI が自分で直し続ける
3. 時間ベース /schedule・ActionsスケジュールやイベントIssue 起点の自律実行を含む。運用方針は現時点で未確定（第3章）
4. プロアクティブAI 自身が仕事を探す今回は対象外。コストと暴走管理が別途必要
現在地

ゴールベースの手前。手順書側の構成（PR 作成 skill・画面確認・ネットワーク遮断）が完了した時点で、検証可能な停止条件さえ与えれば AI が自走できる状態にある。

次の一手

  • 検証 skill — テスト実行と画面確認（コンソールエラーの有無、スクリーンショット比較）を機械判定できる形に落とし込む
  • /goal の停止条件の型化 — 「何をもって完了とするか」を毎回考えるのではなく、再利用できる型として整備する
重要な原則: AI に自分の成果物を評価させない

自己評価は実際の品質より高く出る。したがって作る役と検証する役を分離し、検証は「テストが通ったか」「画面にエラーが出ていないか」といった機械的に判定できる条件に落とし込む。画面確認の仕組み（Playwright MCP、excludedCommands による開発サーバーの解放、日本語フォント導入）を整えたのは、便利さのためだけでなく、この検証役を成立させるための部品でもある。
